# Spike Polylang — constats du lot 0 d'ADR-020

**Fichier** : `docs/architecture/spikes/2026-11-07-polylang.md`
**Rôle** : consigner ce qu'un vrai WordPress a répondu aux hypothèses d'ADR-020 avant d'écrire la première ligne du plugin multilingue
**Date** : 7 novembre 2026
**Reproduction** : `plugin/tests/Integration/wp-cli/polylang-spike.php` puis `plugin/tools/polylang-http-spike.sh` (mode d'emploi dans `plugin/plugin-README.md`)

---

## 1. Pourquoi un spike

ADR-020 a été écrite sur des lectures de code et de documentation, pas sur un site qui tourne. Sa décision repose sur une dizaine de comportements de Polylang gratuit que personne n'avait observés dans ce projet : la création des langues par code, l'attribution d'une langue à un type de contenu custom, ce que fait le paramètre `lang` sur les routes REST, le sort d'un slug réutilisé dans une autre langue, la cohabitation des hreflang de Polylang et de Yoast, la détection de la langue du navigateur. Le lot 0 consistait à installer la stack cible et à faire répondre WordPress lui-même, avant tout autre lot. Chaque constat ci-dessous est reproductible par les deux scripts.

## 3. Constats

Chaque ligne dit ce qui a été observé, puis ce que cela change pour ADR-020.

### 3.1. Côté API, dans WP-CLI

| Hypothèse | Observé | Conséquence |
|---|---|---|
| Les langues se créent par code | `PLL()->model->languages->add(['locale' => 'fr_FR'])` crée la langue avec le nom, le slug et le drapeau de son catalogue ; la première créée devient la langue par défaut ; `en_GB` donne le slug `en` | Le lot 2 peut poser les langues depuis le plugin, sans passer par l'assistant |
| Les réglages se posent par code | `PLL()->options->set()` puis `save()` acceptent les cinq réglages ; `post_types` suffit à rendre `project` et `article` traduisibles, sans le filtre `pll_get_post_types` | Pas de filtre à écrire ; la configuration est de la donnée |
| Un post importé sans langue reste sans langue | Les 16 posts importés avant Polylang n'ont **aucune** langue ; un post inséré depuis WP-CLI sans langue reste à `false` : aucune attribution automatique dans ce contexte | **Confirmé** : l'import appelle `pll_set_post_language` à chaque écriture, y compris sur `Unchanged` si la langue diverge |
| L'API lie les traductions | `pll_set_post_language`, `pll_save_post_translations`, `pll_get_post_translations`, `pll_get_post($id, 'de')` se comportent comme documenté | La `LanguageGateway` du lot 2 n'a que ces quatre appels à envelopper |
| Un slug réutilisé dans une autre langue est suffixé | Une page `cv` en allemand devient `cv-2`, un projet `momocad` en anglais devient `momocad-2` : comportement du noyau, Polylang gratuit n'intervient pas | **Confirmé** : la convention de slugs d'ADR-020 (suffixes `-de`/`-en` pour les fiches, slugs naturels distincts pour les pages) est obligatoire |
| `lang => ''` neutralise le filtre de langue | Dans WP-CLI : sans variable `lang`, 15 projets (toutes langues) ; `lang => 'fr'` 14 ; `lang => 'de'` 1 ; `lang => ''` 15 | Le catalogue peut lister toutes les langues en passant `lang => ''` quand il le faut |
| Les taxonomies du plugin ne sont pas traduites | `tech_tag`, `project_status` et `skill` sont hors des taxonomies de Polylang (réglage vide) | Voir 3.2 : leurs archives vivent hors des préfixes de langue |

### 3.2. Côté visiteur et API, en HTTP

| Hypothèse | Observé | Conséquence |
|---|---|---|
| L'accueil redirige selon le navigateur | `GET /` répond **302** vers `/de/` pour `Accept-Language: de-CH`, `/fr/` sinon, pose le cookie `pll_language` (un an, `SameSite=Lax`) et l'en-tête `Vary: Accept-Language` ; un cookie existant prime sur le navigateur ; **un robot est redirigé comme un humain** | La détection ne porte que sur `/` ; `/fr/`, `/de/`, `/en/` répondent 200 directement. Acceptable pour le SEO avec le `Vary` ; à consigner dans la mention du cookie |
| Une langue sans contenu est proposée au navigateur | **Non** : tant qu'aucun post n'est en anglais, `Accept-Language: en` mène à `/fr/` ; dès qu'un post anglais existe, à `/en/` (Polylang filtre les langues vides, `hide_empty`) | Une langue s'ouvre d'elle-même à la détection quand elle a du contenu ; l'option `portfolio_md_published_languages` d'ADR-020 reste utile pour le sélecteur et le repli, mais Polylang fait déjà la moitié du travail |
| Les anciennes URL sans préfixe survivent | `/projets/momocad/` et `/cv/` répondent **301** vers `/fr/…` ; un mauvais préfixe (`/de/projets/momocad/`) est corrigé en 301 vers la bonne langue | **Confirmé** : la migration vers le préfixe `/fr/` ne casse aucun lien entrant |
| hreflang de Polylang, pas de doublon Yoast | Une fiche avec une traduction porte deux `<link rel="alternate" hreflang>` (fr, de) ; une fiche sans traduction n'en porte **aucun** ; l'accueil porte fr, de, en et `x-default` ; Yoast n'émet pas de hreflang et pose un `canonical` sur l'URL préfixée ; le sitemap Yoast liste les URL `/fr/…` sans hreflang | **Confirmé**. Le `x-default` hors accueil passera par `pll_rel_hreflang_attributes` (lot 5) |
| Polylang intercepte `lang` sur toute route REST et filtre | Il lit bien `lang` (hook `rest_pre_dispatch`) mais **ne filtre rien** en version gratuite : `/portfolio/v1/projects?lang=de`, `?lang=xx`, `?language=de` répondent tous `X-WP-Total: 14` ; `/wp/v2/project?lang=de` renvoie les 15 posts | L'argument « collision » d'ADR-020 est plus faible que prévu : `lang` ne changerait pas nos réponses aujourd'hui. Le nom `language` est **gardé** pour une raison de découplage : Polylang Pro filtre bien les routes natives sur `lang`, et une version future du gratuit pourrait le faire |
| Les archives de taxonomie existent sous `/de/` | **Non** pour les taxonomies non traduites : `/fr/tag/x/`, `/de/tag/x/` répondent **404** ; `/tag/x/` répond 200 et mélange les langues (le DE y figurerait) ; les archives de type, `/de/projets/`, existent (1 fiche) et `/en/projets/` répond 200 **vide** | **Décision à prendre au lot 5** : traduire les termes chez Polylang (un terme par langue, synchronisé par la grille : lourd) ou garder les archives hors des langues et les mettre en `noindex` ; dans les deux cas, une archive de type vide dans une langue fermée doit être gérée par le repli ou par le sélecteur |
| Le catalogue du plugin ignore les posts sans document | La copie allemande créée à la main (sans document Markdown) est servie par WordPress (`/de/projets/momocad-de/` 200) mais **invisible** aux routes du plugin (404, et absente du sitemap) | Attendu : un document traduit doit passer par l'import, comme en français |

### 3.3. Côté administration

| Hypothèse | Observé | Conséquence |
|---|---|---|
| La boîte Polylang s'ajoute à l'écran d'édition | La boîte `ml_box` (sélecteur de langue et table des traductions) est présente sur l'écran classique d'une fiche, à côté de la boîte « Document Markdown » | **Confirmé** : une seconde source de vérité pour la langue ; `wp portfolio translations reconcile` (lot 2) reste la garantie, le masquage de la boîte n'est qu'un confort |
| La modification rapide et en masse portent la langue | La liste des fiches affiche la colonne des langues (drapeaux) ; le gabarit de modification rapide contient le sélecteur `inline_lang_choice`, mais le plugin a **déjà retiré** la modification rapide des posts documentés ; la modification en masse propose encore la langue | Même conclusion : `reconcile` |

## 4. Ce que le spike change dans ADR-020

1. Le paramètre `language` reste, mais pour le découplage, pas pour une collision observée.
2. Les archives de taxonomie ne sont pas « sous une langue secondaire non traduites » : elles sont **hors des langues** (404 sous préfixe, 200 sans). Le choix traduire / `noindex` est posé au lot 5.
3. Une langue vide est déjà masquée par Polylang à la détection du navigateur : l'ouverture d'une langue combine ce comportement natif et notre option.
4. Les robots sont redirigés sur `/` comme les humains ; les pages de langue, elles, ne redirigent pas.
5. Le minimum WordPress réel de la stack est 7.0, imposé par Yoast 28.8, pas 6.8.

Rien n'a invalidé la décision : le critère d'échec (impossible de piloter Polylang de façon fiable depuis l'import) n'est pas atteint. ADR-020 passe en **Accepté**.

## 5. Reste à vérifier plus tard

- La version de WordPress et de PHP disponibles chez o2switch (7.0 et 8.2 au minimum).
- Le sélecteur de langue dans GeneratePress (menu ou widget) et son option `hide_if_empty`, au lot 5.
- Le temps de relecture d'une fiche traduite par Morgan, au lot 6.
- Le prix et les redirections 301 de Polylang Pro, seulement si les bases d'URL françaises sous `/de/` gênent.
