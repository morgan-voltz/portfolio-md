# Spike Polylang — constats du lot 0 d'ADR-020

**Fichier** : `docs/architecture/spikes/2026-11-07-polylang.md`
**Rôle** : consigner ce qu'un vrai WordPress a répondu aux hypothèses d'ADR-020 avant d'écrire la première ligne du plugin multilingue
**Date** : 7 novembre 2026
**Reproduction** : `plugin/tests/Integration/wp-cli/polylang-spike.php` puis `plugin/tools/polylang-http-spike.sh`, dont la section d'administration demande `ADMIN_USER` et `ADMIN_PASSWORD` (mode d'emploi dans `plugin/plugin-README.md`)

---

## 1. Pourquoi un spike

ADR-020 a été écrite sur des lectures de code et de documentation, pas sur un site qui tourne. Sa décision repose sur une dizaine de comportements de Polylang gratuit que personne n'avait observés dans ce projet : la création des langues par code, l'attribution d'une langue à un type de contenu custom, ce que fait le paramètre `lang` sur les routes REST, le sort d'un slug réutilisé dans une autre langue, la cohabitation des hreflang de Polylang et de Yoast, la détection de la langue du navigateur. Le lot 0 consistait à installer la stack cible et à faire répondre WordPress lui-même, avant tout autre lot. Chaque constat des sections 3.1 à 3.3 est produit par l'un des deux scripts ; la colonne « Méthode » dit lequel (CLI pour le script WP-CLI, HTTP pour le script shell, HTTP admin pour sa section authentifiée). Ce qui vient d'une lecture de code et non d'une exécution est dit tel quel.

Réglages de Polylang posés par le script CLI : langues `fr` (`fr_FR`, par défaut), `de` (`de_DE`), `en` (`en_GB`) ; `force_lang = 1` (mode répertoire), `hide_default = false` (préfixe `/fr/` visible), `browser = true`, `redirect_lang = false`, `post_types = [article, project]`. Le script crée aussi, le temps des vérifications HTTP, une copie allemande de la fiche `momocad` (slug `momocad-de`, mêmes tags), une page allemande insérée avec le slug `cv`, et une fiche anglaise.

## 3. Constats

Chaque ligne dit ce qui a été observé, puis ce que cela change pour ADR-020.

### 3.1. Côté API, dans WP-CLI

| Hypothèse | Observé | Méthode | Conséquence |
|---|---|---|---|
| Les langues se créent par code | `PLL()->model->languages->add(['locale' => 'fr_FR'])` crée la langue avec le nom, le slug et le drapeau de son catalogue ; la première créée devient la langue par défaut ; `en_GB` donne le slug `en` | CLI | Le lot 2 peut poser les langues depuis le plugin, sans passer par l'assistant |
| Les réglages se posent par code | `PLL()->options->set()` puis `save()` écrivent les cinq réglages dans l'option `polylang` ; `post_types` suffit à rendre `project` et `article` traduisibles, sans le filtre `pll_get_post_types` ; `save()` répond `false` quand rien n'a changé (relance) | CLI | Pas de filtre à écrire ; la configuration est de la donnée |
| Un post importé sans langue reste sans langue | Les 16 posts importés avant Polylang n'ont **aucune** langue ; un post inséré depuis WP-CLI sans langue reste à `false` : aucune attribution automatique dans ce contexte | CLI | **Confirmé** : l'import appelle `pll_set_post_language` à chaque écriture, y compris sur `Unchanged` si la langue diverge |
| L'API lie les traductions | `pll_set_post_language`, `pll_save_post_translations`, `pll_get_post_translations`, `pll_get_post($id, 'de')` se comportent comme documenté | CLI | La `LanguageGateway` du lot 2 n'a que ces quatre appels à envelopper |
| Un slug réutilisé dans une autre langue est suffixé | Une page `cv` en allemand devient `cv-2`, un projet `momocad` en anglais devient `momocad-2` : comportement du noyau, Polylang gratuit n'a aucun filtre sur `wp_unique_post_slug` (lecture de sa source) | CLI | **Confirmé** : la convention de slugs d'ADR-020 (suffixes `-de`/`-en` pour les fiches, slugs naturels distincts pour les pages) est obligatoire |
| `lang => ''` neutralise le filtre de langue | Dans WP-CLI : sans variable `lang`, 15 projets (toutes langues) ; `lang => 'fr'` 14 ; `lang => 'de'` 1 ; `lang => ''` 15 | CLI | Le catalogue peut lister toutes les langues en passant `lang => ''` quand il le faut |
| Une langue sans contenu est proposée au navigateur | **Non** : la liste des langues « non vides » (`languages->filter('hide_empty')`, celle que Polylang soumet à la détection du navigateur) ne contient pas `en` tant qu'aucun post n'est en anglais, et la contient dès qu'un post anglais existe | CLI, puis HTTP | Une langue s'ouvre d'elle-même à la détection quand elle a du contenu ; l'option `portfolio_md_published_languages` d'ADR-020 reste utile pour le sélecteur et le repli, mais Polylang fait déjà la moitié du travail |
| Les taxonomies du plugin ne sont pas traduites | `tech_tag`, `project_status` et `skill` sont hors des taxonomies de Polylang (réglage vide) | CLI | Voir 3.2 : leurs archives n'ont pas d'URL par langue |

### 3.2. Côté visiteur et API, en HTTP

| Hypothèse | Observé | Méthode | Conséquence |
|---|---|---|---|
| L'accueil redirige selon le navigateur | `GET /` répond **302** vers `/de/` pour `Accept-Language: de-CH`, vers `/en/` pour `en-US` dès qu'une fiche anglaise existe, vers `/fr/` sinon ; pose le cookie `pll_language` (un an, `SameSite=Lax`) et l'en-tête `Vary: Accept-Language` ; un cookie existant prime sur le navigateur ; **un robot est redirigé comme un humain** | HTTP | La détection ne porte que sur `/` ; `/fr/`, `/de/`, `/en/` répondent 200 directement. Acceptable pour le SEO avec le `Vary` ; à consigner dans la mention du cookie |
| Les anciennes URL sans préfixe survivent | `/projets/momocad/` et `/cv/` répondent **301** vers `/fr/…` ; un mauvais préfixe (`/de/projets/momocad/`) est corrigé en 301 vers la bonne langue | HTTP | **Confirmé** : la migration vers le préfixe `/fr/` ne casse aucun lien entrant |
| hreflang de Polylang, pas de doublon Yoast | Une fiche avec une traduction porte deux `<link rel="alternate" hreflang>` (fr, de) ; une fiche sans traduction n'en porte **aucun** ; l'accueil porte fr, de, en et `x-default` ; Yoast n'émet pas de hreflang et pose un `canonical` sur l'URL préfixée ; le sitemap Yoast liste les URL `/fr/…` sans hreflang | HTTP | **Confirmé**. Le `x-default` hors accueil passera par `pll_rel_hreflang_attributes` (lot 5) |
| Polylang intercepte `lang` sur toute route REST et filtre | Il lit bien `lang` (hook `rest_pre_dispatch`, lecture de sa source) mais **ne filtre rien** en version gratuite : `/portfolio/v1/projects?lang=de`, `?lang=xx`, `?language=de` répondent tous `X-WP-Total: 14` ; `/wp/v2/project?lang=de` renvoie les 15 posts | HTTP | L'argument « collision » d'ADR-020 est plus faible que prévu : `lang` ne changerait pas nos réponses aujourd'hui. Le nom `language` est **gardé** pour une raison de découplage : Polylang Pro filtre bien les routes natives sur `lang`, et une version future du gratuit pourrait le faire |
| Les archives de taxonomie existent sous `/de/` | **Non** pour les taxonomies non traduites : `/fr/tag/x/`, `/de/tag/x/`, `/en/tag/x/` répondent **404** ; une seule URL existe, `/tag/x/`, qui répond 200 et dont le contenu dépend de la langue du cookie ou du navigateur : 5 fiches françaises sans en-tête, la seule fiche allemande avec `Accept-Language: de`, rien avec le cookie `en` (`<html lang>` change avec). Les archives de type ont bien leur préfixe : `/de/projets/` liste la fiche allemande, `/en/projets/` répond 200 mais **vide** tant que rien n'est anglais | HTTP | **Décision à prendre au lot 5** : traduire les termes chez Polylang (un terme par langue, synchronisé par la grille : lourd) ou garder ces archives hors des langues, en `noindex`, voire les désactiver au profit des filtres du front React ; une même URL qui change de contenu selon le visiteur ne doit pas être indexée. Une archive de type vide dans une langue fermée est à gérer par le repli ou par le sélecteur |
| Le catalogue du plugin ignore les posts sans document | La copie allemande créée à la main (sans document Markdown) est servie par WordPress (`/de/projets/momocad-de/` 200) mais **invisible** aux routes du plugin (404, et absente du sitemap) | HTTP | Attendu : un document traduit doit passer par l'import, comme en français |

### 3.3. Côté administration

| Hypothèse | Observé | Méthode | Conséquence |
|---|---|---|---|
| La boîte Polylang s'ajoute à l'écran d'édition | La boîte `ml_box` (sélecteur de langue et table des traductions) est présente sur l'écran classique d'une fiche, à côté de la boîte « Document Markdown » | HTTP admin | **Confirmé** : une seconde source de vérité pour la langue ; `wp portfolio translations reconcile` (lot 2) reste la garantie, le masquage de la boîte n'est qu'un confort |
| La modification rapide porte la langue | La liste des fiches affiche la colonne des langues ; le gabarit de modification rapide contient le sélecteur `inline_lang_choice`, mais le plugin a **déjà retiré** les liens de modification rapide des posts documentés | HTTP admin | Même conclusion : `reconcile` |

## 4. Ce que le spike change dans ADR-020

1. Le paramètre `language` reste, mais pour le découplage, pas pour une collision observée.
2. Les archives des taxonomies non traduites n'ont **pas d'URL par langue** : une seule URL sans préfixe, dont le contenu suit la langue du cookie ou du navigateur. Le choix traduire / `noindex` / désactiver est posé au lot 5.
3. Une langue vide est déjà masquée par Polylang à la détection du navigateur : l'ouverture d'une langue combine ce comportement natif et notre option.
4. Les robots sont redirigés sur `/` comme les humains ; les pages de langue, elles, ne redirigent pas.
5. Le minimum WordPress réel de la stack est 7.0, imposé par Yoast 28.8, pas 6.8. L'en-tête du plugin dit encore 6.4 : le relever est une décision à part, liée à l'hébergeur.

Rien n'a invalidé la décision : le critère d'échec (impossible de piloter Polylang de façon fiable depuis l'import) n'est pas atteint. **Proposition** : passer ADR-020 en « Accepté » avec les amendements ci-dessus ; le changement de statut est porté par la pull request de l'ADR, et c'est Morgan qui tranche en la mergeant.

## 5. Reste à vérifier plus tard

- La version de PHP disponible chez o2switch (8.2 au minimum) ; WordPress y est en 7.1.4, ce que la stack locale reproduit.
- Le sélecteur de langue dans GeneratePress (menu ou widget) et son option `hide_if_empty`, au lot 5 ; le spike n'a vérifié que le rendu des pages et des archives sous ce thème.
- Le sort des archives de taxonomie (point 2 du §4), au lot 5.
- Le temps de relecture d'une fiche traduite par Morgan, au lot 6 ; si une fiche demande plus d'une heure par langue, les estimations des vagues de traduction sont à recaler.
- Le prix et les redirections 301 de Polylang Pro, seulement si les bases d'URL françaises sous `/de/` gênent.
